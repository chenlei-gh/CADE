# UI Generator Clarification Policy

> CADE UI Generator 的「不可安全猜测检查器」边界。
> 本文档是**经验性工程边界**，不是 UI Semantic Model，也不是静态本体论。

---

## 1. 目的与边界

本文档回答一个具体工程问题：

> 从用户意图生成正确 CAA UI 之前，Generator 在哪些信息上**不能替用户猜测**？

它描述的是「不可安全推断边界」，而不是「UI 语义的本体」。

**边界声明**

- 指代消歧、领域对象解析（例如「颜色」指 RGB 还是业务字段、「名字」指 Part Number 还是 Instance Name）属于上游 **Domain / Intent Resolution**，不在本文档范围。
- 本文档的四轴只在「Domain 已确定」之后生效。

---

## 2. 四个必要且两两正交的决策轴

| 决策轴 | 核心问题 | 一句话定义 |
|--------|---------|-----------|
| **行为落点** | 变化作用到哪里？ | 用户操作后，被修改的对象是**写 CATIA 领域**还是**只改 UI / 内存** |
| **提交时机** | 什么时候生效？ | 用户编辑产生的修改，是**立即生效**还是**点击 Apply / 确认后生效** |
| **值间约束** | 一个值是否限制另一个值？ | 一个值的改变是否**约束另一个值的候选集合** |
| **选择基数** | 一次可以选几个？ | 从集合中选择时是**单选**还是**多选** |

这四个轴是**必要**的（逐个删除都会导致 S1～S5 中出现无法安全消歧的行为分叉），且**两两正交**（六对组合均无包含关系）。

---

## 3. 四轴各自的触发条件

对每个轴，判断顺序固定为三档：

1. **信息已明确** → 不问。
2. **CATIA API / Domain 模型 / CADE 约定可安全确定** → 自动决定，不问。
3. **存在两个同样合理但行为不同的实现，且无法安全消歧** → 澄清。

判据强调：

- 必须是**行为语义差异**（例如「写 CATIA」vs「只改 UI」），不是控件、布局、Grid、API 选择的差异。
- 「API 能做某事」不等于「本次交互应该做某事」；「通常这么做」不等于「可以安全推断」。
- 按钮名称、控件类型、布局**不是行为契约**。

各轴补充触发细节：

| 轴 | 触发细节 |
|----|---------|
| 行为落点 | 只在「写领域 vs 写 UI / 内存」存在**语义歧义**时触发；无修改动作则不触发 |
| 提交时机 | 只在存在修改 / 提交动作时触发；多步流程中若最终生效时机已明确，中间步骤不追问 |
| 值间约束 | 只在输入出现「筛选 / 联动 / 取决于」暗示，或存在**无法由领域模型推出的业务关系**时触发 |
| 选择基数 | **条件性检测项**：意图已说明「单个 / 多个」则不问；未说明才问 |

---

## 4. 三个边界纪律

1. **行为落点只讨论「直接修改目标」的语义差异**，不讨论实现存储位置、回调、`ClearSelect` 等实现策略。
   - 例：`instName` 写 CATIA vs 写 UI 草稿 → 问（语义差异）。
   - 例：选择结果存 CATIA Selection vs 存 UI checked 数组 → 不问（实现策略，语义等价）。

2. **值间约束只有在存在联动 / 筛选暗示，或存在无法由领域模型推出的业务关系时才检查**，不主动问「两个值有没有关系」。

3. **Domain Resolution 澄清与四轴澄清分层**，不能混在同一个问题列表里。
   - 「颜色是什么」「名字是 Part Number 还是 Instance Name」「转换的目标产物是什么」属于 Domain Resolution，**不由四轴负责**。

---

## 5. 决策流

```text
User Intent
    ↓
Domain / Intent Resolution
    ↓
4-Axis Clarification Check
    ↓
├─ 信息已明确 → 继续
├─ API / Domain / CADE 可安全确定 → 自动决定
└─ 存在无法安全消歧的行为分叉 → Clarification
    ↓
Clarified Intent
    ↓
UI + Behavior + Execution Body
```

四轴是「缺口检测器」，不是「问题生成器」：

```text
发现轴存在 ≠ 发现信息缺失 ≠ 必须提问
```

---

## 6. 证据范围

本文档的结论建立在以下证据之上：

- **样本**：S1（AutoColor）、S2（AutoRename）、S3（BOM Export）、S4（PartToAsm）、S5（BOM Panel）。
- **必要性**：四轴逐个删除测试。
- **正交性**：六对两两组合测试。
- **空跑**：A～G 共 7 条真实用户输入，验证「该问的问、不该问的不问」，含纯只读展示（F）与多步向导（G）两类边界场景。

**注意**：这是当前 CADE UI Generator 的**经验性工程边界**，不是普遍 UI 理论。

---

## 7. Non-Goals

本 Policy **不规定**：

- 控件类型（`CATDlgCombo`、`CATDlgEditor`、`CATDlgPushButton` 等）
- 布局与视觉样式
- CAA API 选择
- Dialog / Command / Applicator / Executor 的具体架构拆分
- Domain Resolution 如何实现
